# AudioCast 중계 중단 진단

## 추가 관찰: 16:52~16:54 실제 멈춤 확인

사용자가 멈춤을 알린 직후 기기와 수신기를 다시 검사했다. 폰의 LiveService와 AAC 생성은 약 50분째 계속되었고 플레이리스트는 sequence 3035 이후로 정상 진행했다. 그러나 홈 그룹 수신기는 `BUFFERING`, `playback_rate=0`이었다. 폰 앱 화면은 여전히 “기기로 전송 중”이라고 표시했다.

로그에 16:50:50.863, 16:53:22.747 `Cast load accepted`가 기록되었고 수신기의 `media_session_id`가 4에서 5로 바뀌었다. 16:53:29~16:54:09 동안 5초 간격으로 요청한 9개 상태가 모두 BUFFERING/rate 0이었다. 새 세션에서도 재생이 복구되지 않았다. 이는 사용자의 “한 번 끊기면 반복된다”는 증상과 부합한다. 다만 관찰한 재로드 간격은 약 152초여서, 단순히 정확한 30초 주기로 반복한다고 표현하면 부정확하다. 송신 앱이 보는 상태와 수신기 상태의 차이 또는 중간 상태 전환 여부는 별도 로그가 필요하다.

따라서 앞선 정상 상태 관찰만으로 안정적이라고 볼 수 없다. **동일 URL 재로드가 성공 응답을 받아도 BUFFERING을 해소하지 못하는 복구 실패를 실제로 확인했다.** 초기 장애 원인과 같은 URL 재로드가 실패하는 세부 원인(수신기 세션/HLS 타임라인/네트워크)은 아직 분리하지 못했다. 앱의 정상 표시 판단과 복구 성공 판단을 실제 수신 재생 진행에 맞게 수정할 필요가 있다. 원본 앱/설정/수신 세션은 이번 재확인에서 변경하지 않았다(상태 조회와 앱 화면 열기만 수행).

2026-10-23, 한국 시간. 증상: 스피커 재생이 멈추고 사용자가 재연결해야 함.

## 결론

캡처/인코더가 종료된 증거는 이번 관찰에서 나오지 않았다. Cast 초기 버퍼링/재로드 흔적과, 연결 상실 뒤 앱 자체의 복구가 불완전한 코드는 확인했다. **최초 멈춤의 직접 원인은 미확정**이다. 네트워크 순간 장애, 그룹 수신기 문제, 짧은 버퍼를 구분할 추가 관찰이 필요하다.

- 저장소: main `5ebf5b3`, 앱 0.36, 최소 지연 15초, AAC 세그먼트 약 4.01초.
- USB 연결 폰: Android test phone, Android 17, 설치 앱 0.43, 지연 목표 6초, 세그먼트 1.002667초.

- 설치/업데이트, 앱 데이터 삭제, 지연 설정 변경은 하지 않았다.

## 확인한 코드의 복구 누락

1. `MainActivity.kt:593`: `onPause()`에서 Cast discovery를 끈다. 다른 앱으로 전환한 동안 앱 자체의 기기 재검색 경로가 비활성화된다. 이것만으로 기존 Cast 재생이 중단된다는 뜻은 아니다.
2. `CastController.kt:65`: 자동 연결은 설정이 켜진 경우에만 기기 발견 이벤트에서 시도한다. `autoTried` 이후 재시도도 제한된다. `tick()`은 세션이 없거나 연결되지 않으면 바로 반환한다. 세션 종료/재개 실패 콜백은 상태만 바꾸고 지속적인 재접속을 예약하지 않는다. SDK의 자체 세션 재개가 실패했을 때 앱이 보완할 경로가 부족하다.
3. `CastController.kt:79`: 재로드 대상은 30초 넘는 BUFFERING과 IDLE의 ERROR/FINISHED뿐이다. 상태가 null/UNKNOWN으로 남거나 PAUSED인 경우에는 같은 `loadedUrl` 때문에 반환한다. PAUSED는 사용자의 의도일 수도 있으므로 무조건 재생시키는 방식으로 고치면 안 된다.
4. `CastController.kt:127~131`: 종료·중단·재개 실패 코드와 실제 플레이어 상태 변화를 진단 로그에 남기지 않는다. HTTP도 요청 총수만 있고 상태 코드/시간/요청 세그먼트가 없어 404·타임아웃 여부를 구분할 수 없다.
5. 설치 앱도 진단 로그가 250줄 순환 버퍼다. 1초마다 HLS 로그가 추가되어 중요한 장애 기록이 약 4분 만에 밀려난다.

위 조건들은 설치 0.43 APK에서도 확인했다. 따라서 버전 차이만으로 생긴 추측은 아니다. 다만 이번 관찰에서 세션 종료를 재현하지 못했으므로, 복구 누락이 과거 모든 멈춤의 직접 원인이었다고 단정하지 않는다.

## 권장 순서

1. **0.43 원본 소스 확보**: 현재 0.36 코드를 폰에 설치하면 이후 버전 변경사항을 잃을 수 있다. 현 설치 앱을 덮어쓰지 않는다.
2. 동일한 홈 그룹에서 지연 6초와 15초를 비교하고, 단일 스피커에서도 비교한다. 6초/그룹 조합만 실패하는지 먼저 분리한다. 이번 조사에서는 설정을 변경하거나 이 비교 시험을 수행하지 않았다.
3. 서비스가 실행되는 동안 명시적으로 켜 둔 자동 재연결을 유지하고, 세션 종료·재개 실패 때 제한된 간격으로 재검색/재접속한다. 사용자 중지·다른 미디어로 전환한 경우는 존중한다.
4. 재생 중이던 자체 스트림에서 상태가 소실되거나 진행이 멈춘 경우를 시간 제한과 함께 감지해 복구한다. 단순 URL 일치만으로 정상 재생으로 판단하지 않는다.
5. 상태 변경, 세션 오류 코드, HTTP 실패/지연을 이벤트 로그에 보존한다. 세그먼트 진행 로그는 빈도를 낮춰 최초 원인이 남도록 한다.
