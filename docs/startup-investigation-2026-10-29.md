# 최초 소리 24초 조사 — 개발 수신기에서 개선 확인

목표: 지연 목표 6초일 때 중계 시작 후 실제 첫 소리까지 9초 이내.

사용자는 홈 그룹 및 거실 네스트 단독 모두 실제 첫 소리가 약 24초라고 확인했다.
송신 로그의 7~9초 PLAYING은 짧게 나타난 뒤 BUFFERING으로 되돌아가므로 청취 성공으로 판정하지 않는다.
캡처한 최초 AAC 세그먼트는 음악을 포함했다. HTTP 요청은 정상 응답하며 짧았다.

## 비교 결과

TARGETDURATION 1/2, 명시적 시작 위치, AAC 코덱을 명시한 master playlist,
2초 세그먼트, 시작 여유 1초, PDT, seek, autoplay=false 사전 로드는
실제 첫 소리 9초 조건을 입증하지 못했다. 사전 로드와 자동 seek 실험은 제거했다.
PC에서 같은 음악의 WAV 및 MPEG-TS HLS 비교도 목표 달성을 입증하지 못했다.
현재 수신기 버퍼 동작이 의심되지만 직접 원인을 확정하지 못했다.

## 수신기 실험 준비

- 미게시 Custom Receiver 앱 E1D7D101 등록. LAN 개발 URL은 receiver/serve.py로 제공.
- PlaybackConfig: autoPauseDuration=0.5, autoResumeDuration=2,
  autoResumeNumberOfSegments=2. MPL HLS 사용. 아직 기기에서 실행되지 않아 효과 미검증.
- 빌드 선택: `assembleDebug -PcastReceiverAppId=E1D7D101`.
  속성 생략 시 기본 수신기 CC1AD845. 테스트 수신기는 등록한 기기만 사용 가능.
- 44.0.6 / 코드50 빌드 및 단위 테스트 통과, 데이터 유지 업데이트 설치.
- 제조사 밑면 사진 QR 번호를 콘솔에 등록했으나, Ready For Testing 표시는
  해당 번호가 실제 거실 스피커의 Cast 번호임을 증명하지 않는다.
- 등록 약 30분 후 재부팅해도 LAUNCH_ERROR reason=NOT_FOUND.
  개발 HTML 요청도 도달하지 않아 재생/버퍼 설정 시험 전 단계에서 막힘.
- Cast 콘솔 탭을 스피커로 전송하면 읽어주는 Cast 일련번호와 대조 필요.
- 미등록 기기가 사라지는 테스트 빌드는 별도 보관하고 기본 수신기 빌드로 복원.

위 시점에는 스토어 및 수신기 공개 배포 없음. 아래 실제 수신기 시험 전까지 24초 문제 해결 또는 9초 청취 성공으로 기록하지 않았다.

## 후속: 실제 Cast 번호 등록 및 첫 청취 개선

사용자가 콘솔 전송으로 확인한 Cast 번호를 등록하고 15분 이후 재부팅하자
E1D7D101이 실제 거실 JBL Link Portable에서 실행됐다. 최초 제조사 라벨 번호 등록은 충분하지 않았다.

- 44.0.6 + 수신기 버퍼2초: 로드6.550초, PLAYING7.054초, 사용자 실제 첫 소리 약12초.
  수신기 audio 요소는 약100초간 waiting/stalled 없이 재생 진행. 9초 목표 미달.
- 44.0.7 / 코드51: 새 수신기 + 지연 목표6초 조합에서만 초기 전송 준비를3초로 단축.
  기존 기본 수신기 및 더 긴 지연 설정의 준비 조건은 유지.
- 최초 시험: 로드3.517초, 연속 PLAYING4.029초, 재시도0.
  사용자는 실제 첫 소리 약3초라고 응답(수동 추정과 송신 로그는 측정 기준/오차가 다름).
- 단위21개, 실패0, 건너뜀1. 새 시험은3세그먼트 공개 조건, 목표오프셋 유지,
  긴 지연으로 변경할 때 준비조건 복원을 검증.

기본 수신기의 재버퍼링 조건이 주된 기여 요인이라는 비교 증거가 생겼다.
그 내부 알고리즘의 정확한 원인을 직접 관측한 것은 아니다.
거실 단독 개발 환경의 결과이며 홈 그룹, 실제 지속 지연, 장기 안정성은 별도 검증 필요.
