# 44.0.3 복구 수정 및 실기기 시험

## 수정

- 표시 버전 44.0.3, 내부 버전 코드 47. 기존 앱 데이터 유지 업데이트 설치.
- 목표 지연 및 초기 준비 조건은 6초 유지. HLS 목록은 최소 18개(약 18초), 메모리 보관은 최소 60개(약 60초)로 분리. 목표 오프셋은 `-6.0` 유지. 실제 청취 지연을 6초로 보장하는 것은 아님.
- 반복 버퍼링 감지 20초에서 12초로 단축. 재시도 간격은 고정 20초로 제한하여 이전의 40/60초 대기 제거. 짧은 PLAYING은 불안정 기록을 지우지 않고, 20초 연속 PLAYING 이후 정상으로 판정.

## 검증

- `assembleDebug testDebugUnitTest` 성공. 20개 중 실패 0, 건너뜀 1(외부 재생 도구/fixture가 필요한 호스트 시험).
- 단위 검사: 6세그먼트 초기 준비 유지, 목표 오프셋 유지, 목록 18개와 보관 60개 분리, 반복 버퍼링 감지, 재시도 간격, 사용자 일시정지 존중.
- Android test phone / Android 17 / 홈 그룹에 6초 설정으로 캡처 중계 시작.
- 시작 직후 버퍼링이 한 번 발생. 20:00:07에 새 로직으로 재로드 후 정상 재생. 최초 6초 준비 시점에는 확장 목록이 아직 가득 차지 않으므로 초기 버퍼링을 완전히 배제하지 못함.
- 폰 Wi-Fi를 명령으로 8초 비활성화한 뒤 finally 구문으로 재활성화. 폰 로그에서 네트워크 상실 20:00:52.891, HTTP 복원 20:00:58.512, Cast 자동 재개 20:01:02.144, PLAYING 전환 20:01:07.994 확인. 수동 재연결 없음. 이 시험에서 HTTP 복원부터 PLAYING까지 약 9.5초.
- 실기기 HTTP 검사: 목록 18개, `TIME-OFFSET=-6.0` 확인. 최신보다 45세그먼트 이전 오디오 요청도 200 응답(24599 bytes). 목록에서 빠진 오디오가 재요청될 때의 여유 보관 확인.

## 한계

시험한 짧은 Wi-Fi 중단의 자동 복구를 확인했다. 모든 네트워크 장애와 장시간 안정성을 보장하지 않는다. Cast SDK가 세션 재개에 실패한 경우의 전체 재접속은 별도 경로다. HTTP 응답 성공과 PLAYING 상태는 실제 스피커 소리의 연속성 측정을 대신하지 않는다. 스토어 배포는 하지 않았다.

원시 로그와 수신기 시계열은 로컬 임시 폴더 `[local path omitted]`의 `44.0.3-device-test.txt`, `44.0.3-baseline.json`, `44.0.3-after-outage.json`에 보관.
